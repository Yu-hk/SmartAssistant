## 5. 测试中发现并修复的问题

1. Word 文档解析因 Commons IO 版本不兼容及递归深度问题失败。
2. 知识摄取默认触发图谱抽取，导致本地模型长时间占用资源。
3. 复合订单号未被完整识别，最近订单未按登录用户查询。
4. 只读订单结果仍重复调用生成模型，导致响应慢或超时。
5. Router 对显式订单号和商品编码缺少确定性快速路由。
6. Router 与 Product 的同步调用协议不一致：Router 发送 JSON，Product 只接收查询参数。
7. Product 使用三条内存样例，未读取 PostgreSQL 中的真实商品和库存。
8. Product 精确命中后仍执行 QueryRewrite/Rerank，单路高质量数据被 RRF 阈值错误拒绝；
   修复前一次请求耗时 134.9 秒，修复后内部查询约 0.18 秒。
9. 页面模型名称硬编码为 `claude-sonnet-4`，与部署的 `qwen2.5:7b` 不一致；
   已重新构建并发布，公网首页和新 JS 均返回 HTTP 200。

- 已于 2026-07-30 将订单知识库切换为 PostgreSQL + pgvector。运行时模型维度为 512，
  `order_knowledge` 共 26 条记录且 26 条均有向量；订单容器重启后数量保持不变。
- `InMemoryKnowledgeBase` 不再进入生产装配，只保留给单元测试和显式
  `app.rag.store.mode=memory` 的本地开发场景。
- 当前环境已显式禁用 OTLP traces/metrics/logs 导出，重启后的 embedding 与 order
  日志均未再出现 `localhost:4318` 连接错误。若后续部署 Collector，可通过环境变量重新启用。
- 前端生产包中 TDesign 主包约 2.1 MB，构建存在大包警告，不影响本次功能验收，
  该项不建议混入本次存储迁移；后续应结合页面级懒加载和路由拆包单独优化。
- 已新增独立的 `POLICY_QA` 意图：通用退换货、运费责任、退款时效等问题优先检索
  `order_knowledge`；包含订单号、最近一笔、我的/这笔订单等明确对象时仍进入订单事实查询。

## 9. 政策问答路由验证（2026-07-30）

- 政策问题“非质量原因退货的运费由谁承担？质量问题时客服还要做什么？”被识别为
  `POLICY_QA`，直接返回 pgvector 检索到的退货判定矩阵及退换货政策，不再要求订单号。
- 具体问题“查询订单 ORD-E2E-0001 的物流状态”仍被识别为 `QUERY_ORDER`，
  返回 PostgreSQL 中的订单事实与顺丰轨迹。
- pgvector 查询运算符由误用的欧氏距离 `<->` 修正为余弦距离 `<=>`，与 HNSW
  `vector_cosine_ops` 索引及相似度计算保持一致。
- 为避免本地生成模型超时，高质量政策知识和高质量只读订单结果均走确定性直接返回。
