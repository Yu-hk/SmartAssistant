审计基线：PR #64。下述完整删除协议仍是拟议设计；已实现范围见 [代次隔离](profile-generation-fencing.md)。
后续新 MQ 消息的内容隔离见 [画像提交引用消息](profile-reference-messages.md)，旧队列内容与跨存储清理尚未完成。
请求级 Redis 发布及新用户索引见 [Redis 原子发布](profile-redis-publication.md)；它不是用户级删除屏障，仍不开放删除入口。
Consumer 新实体事实已接入同一 PG 控制面，见 [实体画像隔离](profile-entity-fencing.md)。
电商画像已补 [入队前准入](profile-request-admission.md)，业务 MQ 不再重启画像分析；
旧实体/文件副本及其他提取入口仍需治理，不把本批视作全量删除完成。
订单 Agent 新记忆已转为 [受控 PG 事实](governed-agent-memory.md)，只接受已准入的本轮原话；
历史文件仍需逐实例清理回执，未自动迁移或删除。
请求投影已补 [Redis 生命周期发布与读取屏障](profile-redis-lifecycle.md)，Router 不再复用内存中的画像正文；
该屏障不替代存储清理回执及备份恢复流程。

## 已确认的产品行为

1. 删除后暂停画像分析，由用户主动重新开启；不因下一次聊天自动恢复。
2. 仅删除画像及其派生副本，保留账号、订单和聊天记录。备份单独跟踪保留状态，
   不把线上清理完成描述为全部物理副本已销毁。若要求同时删除聊天，需另扩展会话/审计/缓存范围。

在跨存储清理协议及回执完成前，不开放生产删除入口，不使用真实用户验证删除。

## PR #64 基线时确认的风险（部分已由第一阶段处理）

| 位置 | 基线行为 | 单纯清库为什么不够 |
| --- | --- | --- |
| `UserProfileSnapshotStore.save` | 快照版本 CAS；变更日志负责 requestId 去重 | 删除快照和日志后，版本归零、去重记录消失；迟到候选可能再次建档 |
| `UserProfileService.commitCandidate` | 版本冲突后根据最新快照重新调用模型 | 删除冲突不能按普通更新冲突重新分析，否则会绕过删除意图 |
| `UserProfileService.buildConversationContext` | 按用户读取旧聊天输入 | 即便没有迟到写入，新一轮仍可能从旧聊天重新生成画像 |
| `PreparedProfileCandidate` / `UserProfileCommitPublisher` | 持久化 MQ 消息含完整报告和本轮用户原话 | 清 PG 和 Redis 不会移除 broker/DLQ 中的副本；当前事件没有独立删除代次 |
| `RoutingKeys` / `publishPrefetchResult` | 投影、候选、完成标记按 requestId 存储 | 缺少完整用户索引；删除与迟到发布存在竞态，TTL 不能代表立即清除 |
| `EntityProfileService` | 直接更新 `user:profile:<id>` | 与 PG 画像是两条写路径，必须一起禁写和清理 |
| `OrderAgentController` / `MemoryExtractor` | 订单回答后异步提取并写 Agent 文件 | 禁用旧模型工具不等于没有文件写入；后台提取同样需要删除代次保护 |

PR #64 的线上盘点表明四个业务容器未挂载共享记忆目录；该信息仅是上次部署观察，
执行前仍需重新核对目录与存储实例。文件锁只保护同一目录的协作进程，不会自动清理其他容器。
提示词审计、执行图、请求缓存可能携带派生画像，需要进一步追踪存储字段；
未完成副本清单前不能承诺“全量画像数据已删除”。

## 拟议控制面

- PostgreSQL 保留最小化 `profile_lifecycle` 控制行：用户、单调递增 generation、
  分析启停状态、删除任务引用、重建证据边界。该行不保存画像内容，也不能随快照一起删除。
- 分析开始前取得 generation；候选、提交消息、Redis 发布、实体事实和文件写入都绑定它。
  禁止在提交时给旧候选补发当前 generation；版本冲突重分析不能跨 generation。
- 删除和提交在同一用户控制行上形成事务顺序。删除首先推进 generation 并禁写；
  校验与持久化不能是无锁的“先检查、后写入”。跨存储写入需要同样的门闩和清理回执，
  不能仅在模型调用前查一次启停状态。
- 中止/失效在途可选分析，但不强杀或重跑订单操作；模型服务端取消不可保证，迟到结果必须丢弃。
- 读取路径立即抑制旧画像，不等后台物理清理结束。已经发往供应商的请求不能靠本地删表撤回。
- 重新开启时进入新 generation，只允许使用重新开启后的合格用户证据。
  仅以日志落库时间或最大消息 ID 作截断不充分：旧请求可能延迟落库，必须保留请求准入代次。

## 可审计清理任务

任务以用户及幂等键唯一标识，只记录操作者、范围、代次、步骤结果和错误类别，不复制待删内容。
状态至少区分：请求已受理、已禁写、在线清理中、部分失败可重试、在线副本已清理。
备份状态独立：待过期/保留中/经核实已移除；不能用一个成功布尔值掩盖未完成目标。

每个存储目标独立回执，失败可幂等重试，进程重启后能继续。某个容器或目录无法核查时，
任务保留未完成状态。多副本情况下按存储实例清点，不能收到同名服务一个回执就声称全体完成。
PG 快照/变更记录、Redis 实体与请求级候选/投影、Agent 文件，以及确认的派生审计副本均需覆盖。
保留必要控制墓碑，防止旧事件重放；删除任务审计本身的保留期限另行设定。

## MQ 与历史版本迁移

建议提交事件改为引用型消息：仅携带用户/请求/候选标识及 generation，
完整候选保存到可按用户清理的受控存储，不继续在新消息中复制用户原话和报告。
旧版消息仍含内容，主队列、未确认消息、重试和 DLQ 必须分别盘点；
阻止其写回不等于物理删除了消息。不能为清一个用户而 purge 全队列。
新老版本共存时不得开启删除入口；仅对旧事件补默认 generation 也不能替代迁移验收。

## 授权与恢复

- 普通用户仅能针对可信登录身份申请，不能通过请求体传入他人 userId。
  管理入口另校验管理员角色与操作者，要求明确目标和确认，不支持默认批量删除。
- 默认关闭删除入口；完成所有写路径覆盖、迁移和演练后再开放。
- 备份恢复必须重放删除墓碑并重新清理已删用户，恢复完成之前不开放流量。
  删除生效后禁止回滚到不识别 generation 的旧二进制；必须准备支持墓碑的兼容恢复版本。
- 历史备份、供应商留存及无法验证的离线副本分别明确范围和状态，不作无法验证的彻底删除承诺。

## 分阶段验收

1. 先实施控制代次与写入隔离、历史证据隔离，保持删除入口关闭。
2. 迁移引用型 MQ 候选，补用户级 Redis 索引和存储实例清点。
3. 加入授权接口、可重试清理任务及逐目标回执；最后再增加页面入口。
4. 使用真实 PG/Redis/MQ 集成测试：删除与提交并发、模型迟到、重复事件、旧 generation、
   删除后重新开启、迟到日志、存储故障、部分失败重试、进程重启及备份恢复。
5. 先本地，再服务器隔离测试；仅操作专属合成用户，正常账号验证只读问答不受影响。
   每批部署验证通过后才推送合并，不因文档编写完成声称删除功能已上线。
