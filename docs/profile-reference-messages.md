# 画像提交引用消息（2026-09-19）

本批继续[代次隔离](profile-generation-fencing.md)，只治理新 MQ 提交消息的内容副本。
不新增画像删除/恢复入口，不删除现有账号、订单、聊天、画像快照或历史队列。

## 数据流与语义

1. 成功对话后的画像候选先保存到 `profile_commit_candidate`，与代次控制行同事务加锁。
   记录按用户、请求、代次唯一；随机候选 ID 不是授权依据，所有读取/完成操作同时限定这些字段。
2. 生产者只发送 v2 引用：版本、用户/请求 ID、候选 ID、代次、请求时间。
   消息正文不包含 `candidate`、画像报告和用户原话；持久消息与 publisher confirm 保持不变。
3. 消费者检查版本及标识，从 PG 解析候选，再走上一阶段的代次隔离提交。
   只有提交返回后才移除暂存内容；提交/存储失败仍抛错，由已有消费重试机制处理。
4. 完成后 `payload` 置空，保留不含内容的回执；重复发布不会恢复内容、刷新过期时间。
   重复消费在完成回执或快照幂等记录处终止，不重复分析。
5. 暂停/失效代次、已完成、缺失或过期候选不自动重新生成，按无效可选工作 ACK。
   数据库故障、损坏的已存候选不是“候选不存在”，必须报错重试。

## 内容保留与可靠性边界

- 暂存候选自首次创建起 24 小时后不可读取。定时任务默认每小时最多清理 500 条过期记录，
  因此不承诺 24 小时内物理清除：停机、故障或积压时更晚；可观测积压与清理回执仍需后续补齐。
- 发布未确认时保留暂存候选，避免结果未知却立即毁掉内容。但本批不是事务 outbox：
  “PG 已保存、尚未 publish 时进程退出”的自动补发未实现，孤立候选最终过期。
  不能把本批描述为恰好一次投递或零消息丢失。
- v1 旧消息仍兼容消费，原有代次隔离继续生效；没有批量重写或 purge 队列/DLQ。
  新消息死信只含引用，但旧消息、旧备份可能仍保存原话与画像。
- 后续 Redis 请求级原子发布和用户索引见 [Redis 原子发布](profile-redis-publication.md)；
  完整删除屏障、实体画像、Agent 文件及请求准入代次仍待治理。
  这不是完整删除协议，也不是所有画像副本已经清除。

## 发布、回滚

先执行 `20260919_add_profile_commit_candidates.sql`，再更新 Consumer；新建库 schema 同步。
单 Consumer 停机切换须暂停入口、排空业务/画像队列后部署，不支持直接让旧 v1 消费者与 v2
生产者并存。多实例环境应先部署兼容读端再启用 v2 写端，本批未提供滚动升级开关。

一旦开始产生 v2 消息，回滚到只识别 v1 的二进制前，必须保留 v2 读端排空全部引用消息，
核查未确认/重试/DLQ 及暂存候选，不能只凭服务健康失败自动回滚旧读端。
非零/暂停的画像代次也继续禁止回滚到未隔离的旧版本。不得为回滚删除控制表或候选表。
