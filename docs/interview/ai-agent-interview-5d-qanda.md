# AI Agent 工程师 · 面试问答模板（5 维对标 SmartAssistant）

> **来源**：《做 AI Agent 开发快一年，企业真正看重的就这 5 点》
> **适用**：AI Agent / LLM 应用 / RAG 工程岗面试备战
> **用法**：每维按「面试官在考什么 → 高频题 → 参考回答骨架（锚定 SmartAssistant 真实实现）→ STAR 素材 → 弱项转化」五段式。要点可直接背诵，也可把 `{占位}` 替换成你自己的项目。
> **核心项目**：SmartAssistant —— 本地化多智能体旅行规划平台（7 微服务 + React 前端 + 自研 RAG 检索管线，离线运行 Ollama `deepseek-r1:7b` + 本地 BGE 向量）。

---

## 0. 一分钟讲清你的项目（所有面试的开场必答）

> 用「做什么 + 技术栈 + 规模 + 你负责什么」四句话收口，别堆功能。

| 要素 | 话术骨架 |
|------|---------|
| 做什么 | 我主导做了一个**本地化的多智能体 AI 助手 SmartAssistant**，面向旅行规划等场景，通过意图路由把用户请求分发给多个专职 Agent 协作完成。 |
| 技术栈 | **Spring Boot 3.5 + Java 21 + Spring AI 1.0.9** 后端，**React + TS + TDesign** 前端，模型走本地 **Ollama（deepseek-r1:7b）+ 本地 BGE 向量**，整体离线可跑。 |
| 规模 | **7 个微服务**（gateway / router / consumer / general / order / product / embedding-service）+ 公共模块，配套 Nacos、PG、Redis、Grafana 监控与 Docker 编排。 |
| 我负责 | 架构设计、RAG 解析层、工具注册与发现、Agent 编排（Graph）、以及从框架选型到部署落地的全流程。 |

**收尾钩子**：「如果方便，我可以从 RAG 脏数据处理或框架原理两个角度，讲两个我踩过、也解决过的真实坑。」（把节奏引向你最强的两维）

## 1. 维度一：Python 工程级能力

**面试官在考什么**：AI 生态 Python 占比高，他想知道你是不是「只会调 API 的脚本小子」，还是能写模块化、可测试、可维护的工程代码。

**诚实定位**：SmartAssistant 主栈是 **Java/Spring AI**，Python 是**检索/算法胶水层**（embedding 服务、数据处理脚本）。不要硬吹 Python 全栈，要讲「工程能力语言无关」+「我在 Python 侧真实写过什么」。

### 高频题 + 参考回答骨架

**Q1：你 Python 到什么程度？平时主要用什么语言？**
- 骨架：主力语言是 **Java（3 年+）**，AI 工程化用 Spring AI 落地；Python 用于**算法/检索胶水层**——独立写过 `embedding-service`（向量化服务）、`embedding_mock.py`、数据清洗与评测脚本。工程素养（模块化、单测、可观测、CI）是语言无关的，我把它从 Java 团队实践平移到了 Python 侧。

**Q2：如果让你用 Python 从零搭一个 Agent，你怎么组织代码？**
- 骨架：`{占位：模块化分层：tools / agents / memory / orchestrator / eval}`；强调**配置与代码分离、类型注解、pytest 覆盖率、日志结构化**，而不是一个 `main.py` 写到底。

**Q3：你更看好 Python 还是 Java 做 Agent 后端？**
- 骨架：看团队与部署。**Python 生态（LangChain/LlamaIndex）上手快但工程化弱；Java/Spring AI 在事务、微服务、可观测上更成熟**。我选 Java 是为了长期可维护与离线可控，但底层检索/向量仍借力 Python 工具链。

### STAR 素材（可选讲）
- **S**：需要本地离线向量化，不能依赖外部 API。
- **T**：写一个轻量 embedding 服务 + 评测脚本，验证 BGE 召回质量。
- **A**：用 Python 实现服务骨架 + 批量评测脚本，输出召回率/精度指标。
- **R**：作为 RAG 质量门禁的一部分，配合 Java 侧检索管线形成闭环。

### 弱项转化
> 若对方强求 Python 深度：「我的差异化是**用工程化语言（Java）把 Agent 做进生产级微服务**，这恰恰是很多纯 Python 团队缺的能力；Python 侧我能快速补齐，且有真实落地代码。」

## 2. 维度二：LLM API 真项目经验

**面试官在考什么**：你有没有**真实跑过** LLM 集成——流式、工具调用、降级、多模型路由，而不是只跑过官方 demo。

**诚实定位**：**强项**。SmartAssistant 是真实多 Agent 生产架构。

### 高频题 + 参考回答骨架

**Q1：你是怎么接 LLM 的？流式输出怎么做的？**
- 骨架：后端用 **Spring AI 的 `ChatModel`** 接本地 **Ollama（deepseek-r1:7b）**；前端走 **SSE 流式**。Consumer 模块做**统一 SSE 入口**——先发 `chat` 触发决策，再用 **Redis 阻塞读（5s）** 取 Agent 产出，实现「边想边出」。

**Q2：工具调用（Function Calling / Tool Use）你怎么实现的？**
- 骨架：用 **`MethodToolCallbackProvider`** 扫描本模块 `@Component` 把方法注册成工具；运行时通过 `discover_tools` 元工具从**工具注册中心**动态发现。工具接口做了**四步法**：Schema 收窄（enum）、错误结构化（`{error_code,message,retryable,hint}`）、副作用审批（ApprovalService 二阶段）、Description 互斥。

**Q3：多 Agent 怎么协作？意图怎么路由？**
- 骨架：Router 模块做**意图理解 → 关键词 → Agent → 兜底**四级链路，叠加**经验体系（ExperienceService）** 与 **Graph 编排（IntentGraph / GraphExecutionService）**，用 **LangGraph4j-core + postgres-saver** 做检查点（Checkpoint）。

**Q4：模型不可用或超时怎么办？**
- 骨架：本地模型 + 离线优先；Consumer 有**上下文压缩**与**会话存储**兜底；工具侧有**超时隔离**（ScriptSandbox 三层防御：黑名单/静态限制/超时隔离）。

### STAR 素材
- **S**：用户问题需要跨多个专职 Agent 协作。
- **T**：既要准确路由，又要可回溯、可干预。
- **A**：设计 Router 四级链路 + Graph 编排 + 经验沉淀；工具注册中心做标签隔离（域/行为/性能）与生命周期（EXPERIMENTAL→ACTIVE→DEPRECATED→DISABLED）。
- **R**：多 Agent 稳定协作，新工具上线零改路由代码。

## 3. 维度三：RAG 脏数据处理（原最弱项，已收口）

**面试官在考什么**：RAG 的瓶颈从来不是「向量数据库」，而是**真实脏数据**——双栏、合并单元格表格、扫描件、乱码。你能不能让检索质量在真实文档上站得住。

**诚实定位**：**曾是最大短板 → 已系统性收口**（Q3 PDF 解析加固）。这是最好的面试叙事：「我定位到瓶颈、设计了方案、写了测试与指标」。

### 高频题 + 参考回答骨架

**Q1：真实 PDF 里的表格、双栏、扫描件你怎么处理？**
- 骨架：自研 **`PdfDocumentParser`**（基于 PDFBox），三层加固：
  1. **表格**：列桶算法识别合并单元格/跨列，输出 Markdown 表格（`pdf-table` 标签），不与正文串味；
  2. **多栏**：按**栏间间隙分段**（而非简单二分），支持三栏以上；
  3. **扫描件**：文本页为空时**自动触发 OCR**，不漏检。

**Q2：OCR 你怎么做？中文生效吗？**
- 骨架：**策略模式**（`OcrStrategy` 接口 + 工厂 `OcrStrategies`）。默认语言 **`chi_sim+eng`**（之前只 eng，已修）；Tesseract 不可用时**优雅降级**到 Noop，并提供 **Ollama 视觉模型**备选。二进制路径可配（系统属性 → 环境变量 → 部署目录 → PATH），附一键安装脚本 `deploy/tesseract/setup-tesseract.ps1`。

**Q3：怎么保障解析质量、怎么发现退化？**
- 骨架：在 `ParsedDocument` 上挂 **metadata 质量指标**（表格数、OCR 是否触发、降级标记）；**WARN 级日志告警**降级事件；核心场景有单测（合并单元格表、多栏、指标、Ollama 降级），外部引擎缺失时 `assumeTrue` 跳过而非失败。

**Q4：检索管线你改了吗？**
- 骨架：**没改自研检索管线**（向后兼容红线），只在**摄入期解析层**加固。这恰恰说明我懂「最小变更原则」——质量提升不破坏既有链路。

### STAR 素材（黄金故事）
- **S**：上线后发现 RAG 召回差，根因不是向量库，而是**摄入的 PDF 解析丢表格/双栏/扫描件**。
- **T**：在不改动检索管线的前提下，把解析质量做扎实。
- **A**：重写了表格（列桶）与多栏（间隙）算法，补上 OCR（中文生效 + 降级 + 视觉备选），加指标与告警，补 4 类单测。
- **R**：表格/多栏/扫描件召回明显提升，且有测试与质量指标兜底，回归稳定。

## 4. 维度四：框架原理

**面试官在考什么**：你是「会用框架」还是「懂框架」？版本踩坑、源码级排查、为什么这么选型，才是分水岭。

**诚实定位**：**强项**。SmartAssistant 因深度使用 Spring AI，被迫做过源码级排障。

### 高频题 + 参考回答骨架

**Q1：你懂 Spring AI 内部原理吗？举个例子。**
- 骨架：懂。比如 **`MethodToolCallbackProvider`** 如何把 `@Component` 方法扫成工具、`ToolDefinition` 的生成、`ChatModel` 的 `defaultOptions` 机制。我们曾在升级中**逐类对比 2.0.0 与 1.0.9 的 API 差异**。

**Q2：你遇到过最深的框架坑是什么？怎么解？**
- 骨架：**Spring AI 2.0.0 ↔ Spring Framework 不兼容（P0）**。`JsonSchemaGenerator` 引用 `org.springframework.core.Nullness`，该类**只存在于 Spring 7 / Boot 4**，而我们用 Boot 3.5（Spring 6.2）。单纯升 Boot 救不了，最终**降级 Spring AI 到 1.0.9 GA**（同时消除 Jackson 注解版本冲突）。根因靠 `unzip -l` 验证 jar 包确认，不是猜。

**Q3：为什么选 LangGraph4j 而不是直接用某个编排框架？**
- 骨架：选 **LangGraph4j-core（零 spring-ai 依赖）+ postgres-saver** 做 Checkpoint；**明确禁用 `langgraph4j-spring-ai` 集成包**（会引入 spring-ai 依赖，与我们版本冲突）。选型基于依赖隔离与可控性。

**Q4：你的工具有生命周期管理吗？**
- 骨架：有独立的 **tool-registry**，按**标签隔离**（域/行为/性能）+ **生命周期**（EXPERIMENTAL→ACTIVE→DEPRECATED→DISABLED），新工具灰度上线、旧工具可退役，不污染主链路。

### STAR 素材
- **S**：Spring AI 2.0.0 一升级，所有 Agent 启动即崩（`NoClassDefFoundError: Nullness`）。
- **T**：定位根因并给出可长期维护的方案。
- **A**：用 jar 包反查确认类只存在于 Spring 7；评估「升 Boot 无效」后决策降级到 1.0.9，并迁移 `OllamaChatOptions→OllamaOptions`、`AssistantMessage` 构造方式等 API。
- **R**：P0 根除，4 个相关单测全绿，团队有了「框架版本兼容」的硬经验。

## 5. 维度五：完整项目闭环

**面试官在考什么**：你能不能从 0 到 1 把一个 AI 项目**做完**——不止模型，还有前端、部署、监控、可用性。

**诚实定位**：**强项**。SmartAssistant 是端到端闭环。

### 高频题 + 参考回答骨架

**Q1：你做过最完整的 AI 项目是什么？**
- 骨架：SmartAssistant——**7 微服务 + React 前端 + 自研 RAG + 多 Agent 编排**，离线运行，配套 Nacos 服务发现、PG/Redis、Grafana 监控、Docker Compose 编排。

**Q2：你怎么做部署和可用性保障？**
- 骨架：容器化编排（多份 `docker-compose`：dev / infra / ha / deploy）；**统一网关**做路由与 JWT 白名单；**上下文压缩**与**会话存储**保对话连续性；监控接 Grafana；关键降级路径（OCR/模型）不阻断主流程。

**Q3：你怎么验证效果？有评测体系吗？**
- 骨架：解析层有**质量指标 + 单测门禁**；工具层有生命周期与结构化错误；规划中有 **eval 系统**（见 `docs/eval-system-gaps-design.md`）做召回/回答质量量化。

**Q4：遇到最大的项目级挑战？**
- 骨架：离线可控 + 多 Agent 协作的一致性。用 **Graph 编排 + 检查点** 解决可回溯，用**经验体系**做持续最优路径沉淀，用**最小变更原则**保证每次重构不破坏既有能力。

### STAR 素材
- **S**：要把一个 demo 级助手做成可长期维护的生产平台。
- **T**：微服务拆分、离线模型、可观测、可扩展工具体系全都要。
- **A**：定架构红线（接口/模型向后兼容、自研管线零改动）、搭工具注册中心、做 Graph 编排与监控。
- **R**：形成可部署、可监控、可扩展的完整闭环，并沉淀出 SOP 与架构文档。

## 8. 避坑清单（不要踩的雷）

- ❌ 不要说「我们的 RAG 用 LangChain 一行搞定」——会被追问脏数据直接露怯。
- ❌ 不要夸大 Python：没写过的深度别编，讲真实胶水层即可。
- ❌ 不要只讲模型效果，不讲工程（部署/监控/降级）——完整项目维度会塌。
- ✅ 每个维度都准备一个**「我踩过、也解决过」的真实坑**，比背概念加分十倍。
- ✅ 遇到不会的：**坦诚 + 给排查思路**，而不是硬编。
