# 画像代次隔离：第一阶段（2026-09-18）

## 范围

这是[全量画像删除协议](profile-erasure-proposal.md)的 PostgreSQL 基础，不是用户删除功能。
不新增删除/恢复 HTTP 入口，不暂停任何现有账号，不清理真实用户画像、订单或聊天记录。
删除后暂停分析、由用户主动重新开启的产品边界已确认；必须完成其余存储治理后才开放入口。

## 已实现

- `profile_lifecycle` 保存用户级单调代次及分析启停状态，独立于快照/去重日志存在。
  控制行不存画像内容；未来删除画像时必须保留该行，不能与快照一起删除。
- 分析开始时捕获代次，异步候选及 MQ 提交一直使用该值。旧消息缺字段只能按代次 0
  处理，不在消费时补发当前代次。普通版本冲突可以重新分析，但不能跨代次重试。
- 写入在同一事务中锁定控制行，校验启停/代次后再做幂等判断、快照 CAS 和变更日志。
  删除与提交必须使用同一行锁形成顺序，避免先检查后写入的竞态。
  锁等待上限 500ms，事务超时 3 秒；存储故障不当作“没有控制行”放行。
- 已失效候选作为明确的非重试结果 ACK，不重新分析、不进入提交失败 DLQ。
- 快照读取过滤暂停状态和错代数据。代次大于 0 时不再把没有准入代次的旧会话日志
  作为新画像证据，仅使用当前问题和本代快照。这仍不等于完整的请求准入隔离。
- 快照和变更日志由显式事务一起提交，保留旧六参数保存入口，但其代次固定为 0。

## 尚未完成，禁止启用全量删除

1. 请求准入代次：排队中的旧业务请求可能在重新开启后才启动分析，不能只依赖模型启动时捕获代次。
2. Redis 请求级候选/投影：发布前检查不是跨存储原子操作，检查后仍可能与删除竞态；
   现有缓存不因本批自动清空。需要用户索引、写入隔离及清理回执。
3. Consumer 新实体事实后续已接入控制面，见 [实体画像隔离](profile-entity-fencing.md)。
   旧 Redis 实体与 Agent 文件仍需治理；文件锁不等于删除代次保护。
4. MQ 仍携带完整候选和用户原话；须迁移到引用型事件并盘点在途/重试/DLQ 的旧内容。
   后续批次已将新消息改为引用，见 [引用消息迁移](profile-reference-messages.md)；旧副本清点仍未完成。
5. 删除任务、幂等恢复、审计副本及备份保留回执未实现；不能承诺物理全量删除。

## 迁移与回滚

先执行 `docs/database/migrations/20260918_add_profile_lifecycle.sql`，再部署 Consumer。
该迁移只增加表及默认 0 的列，既有数据保持可读，不批量插入控制行，也不推进任何代次。
新建数据库的 `docs/database/schema.sql` 已同步。

回滚旧 Consumer 前必须确认没有非零代次或暂停状态；若未来启用删除后再回滚未隔离的旧版本，
可能让旧消息重建画像，应拒绝回滚。控制表/列不得为回滚而删除。
