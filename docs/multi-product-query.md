# 多商品结构化查询

正常商品协议入口的查询、发现、分析和推荐操作，以及直连同步/SSE 入口，均在模型处理前识别 `MultiProductQueryPlan`；优先保留 `_replyScopeQuestion` 中的完整本轮问题。既有 `ProductReadOnlyDispatcher → RESOLVE_READ_ONLY_PRODUCT → ProductFactQueryService` 降级入口复用同一实现。识别成功后由 `MultiProductQueryService` 逐商品调用 `ProductBackend.lookupFacts`，汇总成一次回复；没有新增模型调用、订单报价或写操作。现有 Jev 固定字段建议与 RAG 链继续负责未覆盖的提问。本次没有让 Jev 自由生成商品名或检索条件。

## 范围与关系

支持 2～4 个明确名称/别名/编码，以“和、与、以及、顿号、and、vs”连接；闭合语法识别价格、库存、重量、分场景续航、主动降噪、用途人群、规格、颜色。解析结果保存商品列表、字段、关系、用途、预算值和预算作用范围。所有子查询共享同一字段集合，每个命中的商品节点最多调用 4 次 `lookupFacts`，不为每个商品增加 LLM 调用。当前 SPI 逐项查目录，尚未改为数据库批量 SQL；若上游规划了多个商品节点，仍可能重复核查，本次保证最终回复不重复，不宣称全链路只查一次。

- `耳机A和耳机B分别多少钱？有货吗？`：逐项读取，保留商品身份。
- `耳机A和耳机B哪个更便宜？`：核实价格后计算差额。
- `耳机A和耳机B合计不超过3000元可以吗？`：按每款各 1 件计算总价，并明确未核实运费/优惠；不能把 3000 元套到每个商品上。
- `耳机A和耳机B每款不超过1800元可以吗？`：分别核对单款预算。
- `耳机A和耳机B续航哪个更长？`：显示各自测试场景，不跨场景排名。
- `耳机A和耳机B分别多少钱？哪个更适合通勤？`：显示价格及有来源的用途标签；标签本身不支持“更适合”的性能结论，明确补充依据。

数量如“各两件”、严格小于或复杂数值条件、不同商品各查不同字段、超过四个商品以及混合写请求不走此捷径，原问题交回现有规划链处理。新逻辑不保证现有规划链也能确定性处理这些表达。未知名称不推测为相近商品；多版本要求补充型号；两个别名指向同一个编码时要求确认数量或型号，不重复计价。目录异常返回可重试失败。

## 证据与评估

内部响应 `queryPlan` 保留关系；`productEvidence` 按请求商品记录 RESOLVED / AMBIGUOUS / NOT_FOUND / DUPLICATE_IDENTITY，并在每个字段中记录 `known` 和实际证据文本。`productCoverage` 给出请求/已解析商品数。特征必须具有来源与核验时间；用途标签要求来源与审核记录。兼容性没有专用证据时不得从两份规格推断可配合使用。

这些记录可用于按商品与原子事实检查覆盖率，再对统一回复进行 Ragas 评估；本次添加的是确定性回归和证据输出，没有将 Ragas 模型打分接到线上请求中。`DomainQualityResult.pass` 表示业务处理成功，不是 ContextPrecision 或答案质量达到 1.0。

Router 汇总识别版本化的整题多商品结果：仅当商品域结果的原问题完全一致、闭合语法确定性核验成功且证据项覆盖所有请求商品（包括明确标注未知的商品）时，保留一份完整领域回复，不重复拼接中间查询节点或无结构数据的 general 总结。旧 `ANSWER` 协议入口也保留完整证据，避免仅传递正文后丢失整题标记。订单/知识等其他业务域、结构化 general 输出、不同问题、节点失败、交接及证据冲突不得被该捷径隐藏；原始节点结果继续保留供审计。上游 general 节点可能仍已调用模型，本次只避免最终汇总再润色，不宣称整条请求没有模型调用。

## 验证

`MultiProductQueryServiceTest` 通过真实事实服务入口覆盖分别查询、总/单款预算、价格差、型号歧义、未知商品、别名重复、未知特征、续航场景、用途标签、兼容性和数据源失败，并对未覆盖条件测试完整退出。CI 将该测试纳入 customer-reply-style 门禁。
