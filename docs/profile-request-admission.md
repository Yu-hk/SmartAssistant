# 画像请求准入（2026-09-19）

本批继续 [画像删除协议](profile-erasure-proposal.md)，只收敛电商画像预取的请求准入，
不开放删除/恢复入口，不删除真实用户数据，不改变业务 MQ 格式或重放订单。

## 为什么移到入队前

原来 MQ Consumer 会再次调用画像预取。内存去重只能覆盖同一进程内两分钟，
请求长期排队或进程重启后，旧问题可能重新捕获删除/恢复后的 generation。
现在仅由页面 SSE/会话预处理入口启动可选画像；业务 MQ Consumer 不再启动分析。
进程退出、投影过期或准入失败时，任务正常处理，但不会为了补画像而重跑旧问题。

`ProfileAdmissionStore` 在生命周期行锁下保存不可变准入凭据：用户、请求 SHA-256、
输入 SHA-256、generation 和时间。同一请求/输入/代次幂等；同一请求更换输入或跨代次拒绝。
worker 使用准入所得代次，开始分析前及发布前再次校验，禁止提交时重新获取新代次。
暂停和并发准入由同一 PG 控制行串行化；无控制行仅代表历史代次 0，数据库故障不能视作允许。

## 超时和降级

- 单独的准入线程池：2 个工作位，`SynchronousQueue`，不排队，不在调用线程执行数据库操作。
- 调用方默认最多等待 100ms，配置 `profile.admission.wait-ms` 限制在 20..250ms。
  这是新增、明确有上限的入队前等待，不是“零延迟”；画像模型和商品节点等待上限不变。
- 数据库失败、线程池满载、中断或超时：本轮跳过画像，正常业务继续。
- 取消只是协作式中断；驱动不响应时工作位仍可能被占用。迟到数据库操作最多保存凭据，
  不会通过回调启动模型。准备池满载也跳过，不回退到调用线程执行分析。
- 已准入但未执行完的可选画像不由业务 MQ 重建；这是明确的可用性取舍，不是画像恰好一次保证。

## 保留与边界

凭据不保存问题或报告，但哈希不是匿名化，必须按用户元数据保护。凭据有意不随画像内容清理，
也不自动过期，以免旧请求在清除幂等记录后重新取得新代次；注销账号时由外键级联删除。
大规模长期保留的分区/归档需独立评估，不能直接设置 TTL 破坏防重放语义。

此项覆盖电商画像 `prefetchForRequest` 路径，不声称所有模型、旧实体和 Agent 文件链路已经
完成准入治理。历史直接提取方法仍需纳入后续写路径清单。Redis 用户级墓碑、读取端隔离、
Agent 自动文件写入、派生审计副本、逐目标清理回执和备份恢复仍是删除入口的前置条件。

## 验证及发布

迁移：`20260919_add_profile_request_admission.sql`，只新增表，不修改现有画像或代次。
先迁移再升级 Consumer；回滚保留新增表及凭据，不回滚到忽略生命周期的二进制。
8 项真实 PG 测试覆盖幂等、输入冲突、暂停、恢复拒绝旧请求、内容清理后凭据仍在、
用户隔离、并发准入、事务失败；另有超时/过载/中断和延迟 worker 测试。
删除/恢复仅在隔离测试库使用合成用户执行；生产验证只发起正常只读/缺参澄清问答。
