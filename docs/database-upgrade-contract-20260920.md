# 仓库迁移与恢复后契约验证（2026-09-20）

本轮完成的是**当前仓库合并 schema 的升级、逻辑恢复与删除控制重放自动化门禁**。
不是生产库自动迁移器，也不是逐个历史版本或全站灾备认证。生产数据库、应用、Redis、MQ、
文件及真实控制目录均不写入；没有重启业务服务。

## 可执行路径

```sh
python -m unittest discover -s scripts -p 'test_database_*py' -v
python scripts/database_bootstrap_drill.py --repo . \
  --image pgvector/pgvector:0.8.0-pg16 --with-migrations \
  --report new-upgrade-report.json
```

沿用唯一标签、完整容器 ID 校验、禁网、无宿主绑定/命名卷、限额 tmpfs 和失败清理保护。
只有自身创建的 PG16 容器会被操作，不能传入生产地址。报告拒绝覆盖，SQL 错误只报告 SQLSTATE。

`database_upgrade_contract.py` 显式列出全部 27 个迁移，新增/移除迁移须同时审查顺序；
结构化商品字段先于商品录入、画像生命周期先于独立控制迁移。
迁移输入 SHA-256 写入报告，校验的是原始字节。

演练专用 `fixture_migration_history` 以事务级 advisory lock 串行化：已执行且摘要相同则跳过，
同名不同摘要拒绝；业务 DDL 和记录在同一事务中提交。四个已审阅文件的外层事务显式解包，
其余事务控制拒绝，不声称这是通用 SQL 解析器。
**该记录不能直接搬进生产作为历史基线**。基线已经含有部分增量结构，测试通过不证明
每个 `CREATE TABLE IF NOT EXISTS` 分支都在某个真实旧版本上执行过。

## 实际验证内容

- 执行 27 个迁移，再次运行全部迁移：不重写人工改价，不把 `ACTIVE_RUNNING` 会话重置为闲置；
  迁移记录及时间不变。历史原始 SQL 中的商品更新和会话修整不是无副作用重入，禁止用遍历 SQL 目录代替版本管理。
- 同名迁移摘要变更拒绝；中途制造除零错误，DDL 与迁移记录均不残留；修正后可重试。
- 真正 `pg_dump`/恢复后，对 39 张 public 表（38 张业务表加 1 张演练记录表）的内容摘要、列、约束、
  索引、序列，以及非扩展函数定义、触发器定义和表/序列 ACL 逐项比较。
- 恢复前后实际执行会话唯一性、商品正数约束、订单外键、工作流发布元数据约束、更新时间触发器。
- 专用 `NOLOGIN` 最小权限角色：允许读商品，拒绝改价、拒绝读取账号；包含 ACL 的逻辑恢复后再次验证。
  不验证真实部署账号、集群级角色密码、所有者映射或全部 SECURITY DEFINER/函数执行权限。
- 在恢复后的合并 schema 上调用已发布的 `profile_control_recovery.replay_sql`：失败时原子回滚，
  重放幂等、冲突控制拒绝，已删除画像不复活，其他用户画像与原始聊天保留。
  五项跨存储清理收据必须重新成为 `PENDING`，**不能把 PostgreSQL 成功标成全存储已完成**。

## 发布与验收边界

本地 Docker 引擎不可用；本地执行 Python 防护测试（普通模式及 `-O`），不冒充本地真实 PG 测试。
服务器实际验证放在 `/opt/smart-assistant/releases/database-upgrade-20260920`，仅含合成数据与公开种子。
第一轮暴露测试器权限负例调用参数错误，已修复并增加回归；失败报告 `attempt1.json` 保留。
`attempt2.json` 是加入完整 schema 删除重放前的成功证据；加入完整 schema 后发现测试账号显式 ID
与 `GENERATED ALWAYS` 冲突（428C9），改为仅在合成种子中明确 `OVERRIDING SYSTEM VALUE`，
未放宽数据库身份列。失败报告 `verified.json` 保留；最终以 `verified-final.json` 和
`bootstrap-recheck.json` 为准，不能混用早期报告证明后加代码。
CI 同一作业分别执行基础与升级两条路径，任何一条失败都阻止合并。

`initialSeedRows=20` 仅描述升级前的基础种子，不是升级后的总行数。最终升级路径也在
Python `-O` 模式下执行，避免依赖可被优化掉的 `assert` 宣称数据库契约通过。

以下不能标为完成，也不通过测试时删除真实历史原件来消除缺口：

1. 没有逐版本数据库快照/可信迁移历史，不能认证“任意历史版本一键升级”。
2. 没有在生产执行 PG/Redis/MQ/文件联合回滚。队列可能携带已执行操作，Redis 包含执行权，
   不能简单恢复旧镜像或清空存储；必须按独立控制和业务幂等记录核验，未知操作保持结果未确认。
3. 历史分区/统计辅助函数仍有未启用的依赖；本轮只比较其定义，不宣称其全部运行行为可用。
4. 独立控制目录仍在同机，只覆盖数据库回滚，不覆盖整机丢失。真实隐私页面视觉验收另列，不能以数据库测试代替。

生产恢复仍依照 [画像恢复规程](profile-production-deletion-20260919.md) 保持入口关闭，
先核对固定来源与控制链，重放控制，再验证派生数据清理、业务幂等和队列状态，最后才由运维开放入口。
本轮没有新增自动开流量或自动重投业务消息的脚本。
