# 商品查询容错与检索分层（2026-09-18）

## 已确认故障

2026-09-18 09:08（北京时间）请求 `76f0ad95-8795-4853-875f-922dc38b1e63` 的意图分析、任务规划、查询改写与商品生成收到模型接口 `402 Insufficient Balance`。不是商品未找到或缺货。原通用失败字符串掩盖了执行状态，且只读询价复用了支付/退款风险提示。

## 第一批实现

- `ModelCallFailure` 保留模型执行失败类型；余额/认证错误不在 LLM 网关内重试。意图分析遇到此类错误直接结束，不继续任务规划和商品生成。
- Product 将模型异常转换为失败质量与协议状态，避免普通字符串被当作正常商品回答。Router 对已确认只读失败使用查询提示，未知/写操作仍保留重复操作风险提醒。
- Router 向 Product 发出 `RESOLVE_READ_ONLY_PRODUCT` 只读能力探测；Product 以封闭语法确认完整请求，精确数据库匹配名称/去末尾版本括号的唯一名称，不靠品牌常识猜商品。
- 唯一商品的价格、库存、规格、颜色直接从类型化事实生成答复。歧义需澄清，未知字段不能当成缺货或零价格；涉及写操作、文档限定、额外业务或不支持的句式返回未承接，保留原流程。
- 连续追问仅向前读取有界用户问题，遇到无法识别的上轮问题不跨越推断。此批不实现无限会话实体记忆。
- 只读探测连接超时 1 秒、读取超时 2 秒；不回退到旧模型端点、不进行标题模型抽取。记录真实目录查询工具调用与零生成 Token，不声称数据库查询没有工具开销。
- 保留安全护栏、用户资料隔离、用户身份、预算边界和正常统一后处理；该路径答案不进入语义缓存。未配置类型化事实查询的后端不伪造目录数据。

余额恢复和账户变更属于外部配置，本批不充值、不切换 API Key、不配置未经授权的供应商。

## 后续批次（设计，不是已实现能力）

1. Consumer 商品录入：标准品类、人工确认的名称别名、连接方式和佩戴类型，持久化原文证据、确认人及时间。没有依据的字段保持未知，不能根据名称自动补事实。
2. Product 需求解析：具体型号查询与按需求发现分开；“蓝牙耳机”解析为品类与连接属性，不把它作为 AirPods 的同义词。
3. 检索：精确名称/别名定位；结构化属性和预算先筛选；语义检索只补充候选，不决定价格、库存或硬条件。所有后端都必须遵守未知属性不能满足明确要求的契约。
4. 复杂推荐：模型仅基于核实候选解释匹配理由。独立可用、事先授权的备用模型与余额告警另行配置，不能假设换同账户模型即可恢复。
