# 商品任务的可选画像

画像提升个性化质量，不是商品查询或推荐的业务前置条件。当前用户明确的预算、品类、用途等要求始终优先于历史偏好。

## 执行流程

1. Consumer 将画像工作提交给 `profilePreparationExecutor`，Redis 标记、快照读取、历史读取和模型调用都不在 Chat/SSE/MQ 调用线程执行。情绪分析仍在独立线程池同时进行。
2. 若有可靠的已保存快照，立即发布其安全投影；不等待本次模型更新。没有可靠快照则等待后台分析。
3. 第一个 Product 节点启动可选画像选择，默认预算 **500 ms**。预算包含读线程排队、Redis 调用和轮询；采用单调时钟，慢 Redis 调用不会让业务线程无限等待。
4. 就绪则选用画像；超时、缺失、失败、异常状态或线程池拒绝则选用空画像。这个选择按用户和 requestId 缓存，后续并行/串行商品节点复用同一结果，不重复等待，也不接收迟到结果改变本轮上下文。
5. 商品节点正常查询、比较、推荐。画像异常不记录商品节点失败、不增加熔断失败计数、不将 MQ 业务请求标成不确定执行。Redis 执行权、鉴权与取消标记仍是业务安全条件，不因画像可选而降级绕过。
6. 成功对话在 `profileCommitExecutor` 上等待并发布有效更新候选，沿用原有版本化数据库快照与 MQ 提交流程。显式调度不依赖 Spring AOP；超时/失败返回的 `KEEP` 不提交、更不覆盖已有快照。已有画像可用与新候选准备完成使用不同标记，避免混淆。

用户取消在画像等待前后检查，线程中断/取消异常继续传播，不能当作画像读取故障后继续执行商品操作。

## 边界与资源

- `ROUTER_USER_PROFILE_WAIT_TIMEOUT_MS` 默认 500，运行时限制在 0–2000 ms；0 表示不等待画像。
- `ROUTER_USER_PROFILE_POLL_INTERVAL_MS` 默认 25 ms。
- Router 画像读取池：2 个线程、32 个等待任务，拒绝时直接无画像继续；后台读取超时尝试中断，不能保证驱动立即终止 I/O，但有界线程池限制资源占用。
- Consumer 画像准备池、提交池、模型池分别为 2 个线程、32 个等待任务，均不使用 CallerRunsPolicy。模型等待仍默认最多 8 秒，包含模型池排队时间。
- 同一进程中的画像准备按用户、requestId、问题 SHA-256 去重 2 分钟，最多 10000 项，不把原始问题作为常驻缓存键。没有 Redis/线程池配置时跳过画像，禁止回退为同步执行。
- Router 选定画像为实例内缓存，最多 10000 项、保留 1 小时；不承诺跨实例迁移、重启或超出保留期的恢复流程仍保有相同选择。当前正常请求由同一 Router 执行，远短于保留期。
- 画像准备/提交线程池满时允许丢弃本轮个性化更新，不能挤占业务线程。后续请求可重新分析；这不是长期画像更新“必达”保证。

## 验证和发布

测试覆盖慢 Redis（含忽略中断）、画像失败/过期/缺失、整轮共享等待预算、并行节点共享读取、已选画像保持不变、账号缓存隔离、线程中断、已有画像提前发布、模型 KEEP 不覆盖快照、画像线程池过载、无 AOP 的提交调度，以及情绪/MQ/商品入口降级。

发布需要同时更新 Consumer 和 Router，前端不需要改动。若线上显式设置了旧的 `ROUTER_USER_PROFILE_WAIT_TIMEOUT_MS=10000`，应同步改为 500，而不是依赖默认值。此文件描述实现和本地验证，不表示已部署或完成线上复测。
